# Candela Harness: Architecture Decisions

> Last updated: 2026-06-30

## Overview

The candela-harness is a Rust binary that acts as an IDE sidecar, bridging
IDE extensions (VSCode, JetBrains) to AI model APIs. It provides session
management, streaming chat, cost tracking, and local search.

```
IDE ←→ [JSON-RPC/stdio] ←→ candela-harness ←→ [HTTP/SSE] ←→ Model APIs
                                  ↓
                           SQLite (sessions, messages, FTS5)
```

## ADR-1: Vendored proto-generated types

**Decision:** Vendor proto2type-generated Rust files into `rust/crates/candela-types/`.

**Context:** The shared type contract (Session, Message, ChatEvent, etc.) is
defined in `candela-protos` and code-generated by proto2type. We needed to
decide between vendoring the generated files or adding a build script that
runs `buf generate` at compile time.

**Rationale:**
- Protos change infrequently — vendored files stay fresh with minimal effort
- Zero build dependencies (no buf/protoc in Rust build graph)
- Instant compilation — no codegen step
- Generated files have `// Code generated by proto2type. DO NOT EDIT.` headers

**Regeneration:**
```bash
cd /path/to/candela-protos
buf generate --template buf.gen.rust.yaml
cp gen/rust/.../session.type.rs     ../candela/rust/crates/candela-types/src/session.rs
cp gen/rust/.../session_sqlite.type.rs ../candela/rust/crates/candela-types/src/session_sqlite.rs
cp gen/rust/.../chat.type.rs        ../candela/rust/crates/candela-types/src/chat.rs
cp gen/rust/.../chat_sqlite.type.rs ../candela/rust/crates/candela-types/src/chat_sqlite.rs
```

**Future:** Add CI check (`buf generate --diff`) that fails if vendored files
are stale.

## ADR-2: Proxy-first model routing

**Decision:** The harness talks OpenAI-compatible `/v1/chat/completions` to
the candela proxy by default, with direct Gemini API as fallback.

**Resolution order:**
1. `CANDELA_PROXY_URL` → proxy handles auth, routing, cost tracking
2. `GEMINI_API_KEY` → direct to `generativelanguage.googleapis.com`
3. Neither → error with guidance

**Rationale:**
- The candela proxy already handles multi-provider routing, auth, and cost
  tracking — don't duplicate that logic in the harness
- For local dev without the full stack, a single `GEMINI_API_KEY` should work
- OpenAI-compatible format is the de facto standard; any provider proxy speaks it

## ADR-3: Environment-based configuration

**Decision:** Use environment variables for harness configuration. No config file.

**Variables:**
| Variable | Required | Default | Purpose |
|----------|----------|---------|---------|
| `CANDELA_PROXY_URL` | No | — | Candela proxy URL |
| `GEMINI_API_KEY` | No | — | Direct Gemini API key (fallback) |
| `CANDELA_MODEL` | No | `gemini-2.0-flash` | Default model |
| `CANDELA_SAVE_DIR` | No | `~/.candela/sessions` | SQLite storage path |
| `CANDELA_BUDGET_USD` | No | `5.0` | Per-session budget limit |

**Rationale:**
- The harness is an IDE sidecar — the IDE extension sets env vars when spawning
- Config files add a second source of truth that goes stale
- IDE extensions store persistent settings in their own configuration

## ADR-4: No agent framework

**Decision:** The harness is a thin transport + storage layer. No agent framework
(no Antigravity SDK, no Google ADK, no custom agent loop).

**Rationale:**
- The harness relays chat — it doesn't orchestrate agents
- Intelligence comes from the model's native function calling, not a local loop
- Single static binary with sub-millisecond startup (IDE extensions are latency-sensitive)
- Python runtime dependency (ADK) is unacceptable for an IDE sidecar
- Tool calling, if needed, uses the model's built-in function calling protocol

## ADR-5: Rust, not Go/Python/Zig

**Decision:** The harness is written in Rust.

**Rationale:**
- Single static binary — ships as one file, no runtime
- Sub-millisecond startup (critical for IDE sidecar)
- Existing Rust workspace in the candela monorepo
- Type safety for streaming/async code
- `rusqlite` with bundled SQLite — no system dependency
